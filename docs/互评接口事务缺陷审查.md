## 二、缺陷概述

互评提交接口在一次请求中连续执行 4 次数据库写操作，但整个函数只有末尾一次 `db.commit()`，且**全程没有任何显式回滚**。一旦中途出错，已写入的半成品数据可能随同一次事务被一并落库，造成「互评记录已保存、任务状态未更新、审计链断裂」的不一致状态。

## 三、缺陷定位

- 文件：`backend/app.py`
- 函数：`submit_review()`（`@app.post("/api/reviews")`，起始行 1991）
- 缺陷段落：原第 2046—2069 行（写库段）

该段实际包含 4 次写操作：

1. `INSERT ... ON CONFLICT DO UPDATE` 写入 `peer_reviews`（互评分数与评语）
2. `UPDATE review_assignments` 把分配任务状态改为 `completed`
3. `refresh_review_alert()`：互评分标准差超过 20 时插入 `review_alerts` 偏差告警
4. `audit()`：插入 `audit_logs` 审计记录（含哈希链 `previous_hash → entry_hash`）
5. 末尾 `db.commit()` 一次性提交

## 四、缺陷分析

**1）事务边界依赖隐式行为。** `get_db()` 使用 `sqlite3.connect(DB_PATH)`，默认 `isolation_level=""`，即 Python 会在第一条 DML 前隐式 `BEGIN`、需要显式 `commit()` 才生效。这在数据层面"碰巧"保护了成功路径，但异常路径完全交给连接关闭时的隐式回滚，语义不明确，也不符合项目其它写操作的显式事务约定。

**2）缺少显式 `rollback()`，异常可能被中间层吞掉。** 全文件检索 `rollback` 命中 0 次，说明整个后端没有任何一处主动回滚。而项目里确实存在吞异常的写法，例如 `create_team`：

```python
try:
    ...
    db.commit()
except sqlite3.IntegrityError:
    return abort_json("团队名称已存在")
```

一旦 `submit_review` 的写操作抛出的异常被类似的 `try/except` 就地拦下而没有 `rollback()`，`g.db` 这个**请求级复用连接**上就残留了未提交事务；本次请求后续任何一次 `db.commit()`（例如响应前的其它写操作）都会把这份半成品一起提交。这正是原子性失效的真实路径。

**3）失败反馈不明确。** 异常会冒泡到全局 `unexpected_error`，用户只看到"服务器处理失败，请稍后重试"，无法判断互评是否已部分写入，也无法判断能否重试。

**4）审计链存在不一致风险。** `audit()` 依赖 `audit_logs` 最后一条的 `entry_hash` 计算链式哈希。若审计写入与业务写入不在同一事务，可能出现业务已提交但审计缺失，后续 `verify_audit_chain()` 校验时链路断裂。

## 五、修复方案

将 4 次写操作与 `commit()` 统一纳入一个显式事务边界，异常时显式回滚并返回明确错误。

```python
    db = get_db()
    dimensions = dict(dimension_values)
    try:
        db.execute(...)          # 1. 写入 peer_reviews
        db.execute(...)          # 2. 更新 review_assignments 状态
        if not save_as_draft:
            refresh_review_alert(project_id, target_team_id)   # 3. 偏差告警
        audit(...)               # 4. 审计留痕
        db.commit()              # 5. 全部成功才提交
    except Exception:
        db.rollback()                       # 任何一步失败，整体撤销
        app.logger.exception("互评提交失败，已回滚")
        return abort_json("互评提交失败，本次操作已回滚，请稍后重试", 500)
```

关键点：

- `commit()` 移入 `try` 内部，与写操作同属一个事务单元，避免"提交发生在保护范围之外"
- `except Exception` 中先 `rollback()` 再返回，保证连接不残留未提交事务，杜绝半成品被后续 `commit()` 带走
- 用 `app.logger.exception()` 记录完整堆栈，便于排查
- 返回结构化 JSON 500（`abort_json`），与全站错误响应格式一致，前端可直接提示

## 六、验证过程

1. **语法检查**：`python -m py_compile backend/app.py` 通过
2. **回归测试**：`python -m unittest tests.test_app`，24 个用例全部通过（含互评相关用例）
3. **事务边界核对**：`refresh_review_alert()` 与 `audit()` 内部均无独立 `commit()`，仅做 `execute`，因此并入同一事务不会产生隐式提交，事务边界完整
4. **功能验证建议**：
   - 正常提交一次互评：`peer_reviews` 与 `review_assignments.status` 同时更新，审计表新增一条记录且哈希链校验通过
   - 保存一次草稿：状态回到 `pending`，`completed_at` 置空
5. **回滚验证方法**：临时将第 2 条 `UPDATE` 的表名改为不存在的表触发 `sqlite3.OperationalError`，请求返回 500 且 `peer_reviews` 中无该次互评记录，说明回滚生效（验证后立即恢复语句）

## 七、影响面评估

- 仅改动 `submit_review` 内部实现，**接口路径、请求参数、响应结构均未变化**，前端无需调整
- 正常路径行为不变，失败路径从"隐式 500"变为"显式 500 + 明确提示"
- 事务范围只覆盖本函数内的 5 个写/提交动作，不跨请求，不影响其它接口

## 八、遗留风险与改进建议

本次仅修复互评提交接口。同一模式（多次写 + 末尾单次 `commit()` + 无 `rollback()`）在 `backend/app.py` 中普遍存在，例如项目创建与发布、成果提交、成绩发布、成绩复核申请等接口，均建议后续统一抽取事务装饰器或 `with db:` 上下文封装：

```python
@transactional
def handler():
    ...
```

以便在全站范围内统一事务边界与异常回滚策略，避免逐个接口修补。

# 高校课程项目协作与评审平台设计报告
## 一、引言
### 1.1 项目背景
在高校软件工程等项目驱动式课程教学中，传统依靠微信群、Excel表格、邮件完成组队、成果收集、同伴互评、成绩统计的模式存在诸多痛点：团队协作过程不透明，教师、助教难以实时掌握小组项目进度；迭代成果缺少版本管理，材料归档繁琐；同伴互评容易出现人情分，缺少匿名防干扰机制；多维度成绩手工汇总核算工作量大，容易出现计算错误；关键节点缺少统一通知提醒，操作过程缺少审计追溯。

为解决上述教学痛点，开发**高校课程项目协作与评审平台**，实现从课程项目发布、学生组队分工、迭代成果提交、匿名同伴互评、助教过程检查、教师终评、成绩自动核算导出全流程数字化闭环。本系统采用前端浏览器单页应用+后端Flask服务+SQLite数据库架构，面向教师、助教、学生、教务管理员四类角色，支撑项目制课程教学管理工作。

### 1.2 设计目标
1. 实现课程、项目、迭代任务的管理，支持教师配置评分权重，发布/草稿保存项目任务。
2. 实现学生团队管理，支持创建团队、申请加入、组长审核，支持教师管理员例外调整团队成员，全部变更操作留痕审计。
3. 实现迭代成果上传提交、版本回溯、撤回，助教过程检查、退回修改功能，限制文件格式与大小。
4. 实现匿名同伴互评模块，系统自动轮转分配互评任务，支持草稿保存、异常打分预警。
5. 实现多维成绩自动加权计算，支持个人成绩折算系数、人工扣分，成绩快照归档，支持Excel/PDF导出，成绩复核申诉。
6. 实现站内通知系统、完整审计日志，关键操作哈希链防篡改，完成权限隔离与数据隐私保护。

### 1.3 范围与读者
本设计报告描述系统的类设计、体系结构、内外接口设计。系统范围包含课程项目管理、团队协作、成果提交、互评评审、成绩核算、审计日志模块；不包含在线代码运行、学校统一身份认证、即时聊天、自动查重等功能。
报告面向软件工程课程设计评审，适合开发人员、测试人员阅读，基于前期需求分析文档与前后端源码开展设计。

## 二、设计概述
### 2.1 总体设计思想
系统遵循分层架构思想，分为**前端表现层、后端业务逻辑层、数据持久层**。
- 前端：浏览器单页SPA，原生JS渲染页面，维护全局状态，通过fetch与后端RESTful API交互，完成页面渲染、表单校验、弹窗模态框交互。
- 后端：Flask Web服务，接收前端HTTP请求，完成身份鉴权、CSRF安全校验、业务逻辑处理、权限判断，调用数据库完成数据读写。
- 持久层：SQLite关系数据库，存储业务数据，审计日志采用SHA‑256哈希链实现篡改检测；上传文件存储在本地文件系统。

设计原则：
1. **角色权限隔离**：教师、助教、学生、管理员严格区分访问权限，数据行级可见性控制。
2. **业务状态驱动**：核心对象（提交记录、互评、成绩发布）依靠状态流转约束业务行为，状态非法则拒绝操作。
3. **操作可审计**：所有关键业务动作写入审计日志，形成哈希链，支持管理员校验完整性。
4. **容错与安全**：输入校验、防并发覆盖乐观锁、CSRF防护、异常友好提示，区分业务异常和系统异常。

### 2.2 系统模块划分
|模块名称|模块职责|
|---|---|
|课程项目管理模块|课程创建、项目新建/编辑、迭代阶段管理，配置评分权重，项目草稿与发布控制|
|团队与任务模块|学生建组、入队申请审核、成员任务分配，成员变更留痕|
|成果提交模块|迭代成果上传、版本管理、撤回提交、文件校验，助教过程检查退回|
|同伴互评模块|开启/关闭互评，盲盒轮转分配互评任务，三维打分、草稿保存，异常评分预警|
|成绩管理模块|过程分录入、教师终评录入，团队&个人成绩自动计算，成绩发布/撤回，导出归档，成绩申诉复核|
|通知审计模块|站内消息通知，审计哈希日志，数据库备份，日志完整性校验|

### 2.3 核心业务约束回顾
1. 评分权重：互评、过程分、终评三者总和必须等于100%。
2. 团队人数：3‑5人，组队截止后学生不能自行变更，教师例外调整必须填写理由留痕。
3. 互评规则：学生不能评审自己团队，每人最多评审3个其他团队；互评分去除极值后取平均。
4. 个人成绩公式：`个人成绩 = max(0, min(100,团队总分 × 折算系数 − 人工扣分 − 缺评扣分))`。
5. 成绩发布后进入只读归档，修改必须撤回发布重新生成快照。

### 2.4 主要技术选型
|层级|技术选型|说明|
|---|---|---|
|前端|原生JavaScript、HTML、CSS|SPA单页面，无框架，动态渲染DOM，SVG图标|
|后端|Python Flask|Web后端，REST接口实现业务逻辑|
|数据库|SQLite|嵌入式关系数据库，开发演示便捷|
|报表导出|openpyxl、reportlab|生成Excel、PDF成绩归档文件|
|安全|SHA‑256哈希链、CSRF token、密码加盐哈希|审计防篡改、接口安全防护|

### 2.5 核心状态流转表
| 对象 | 当前状态 | 触发动作 | 操作角色 | 前置条件 | 下一状态 | 审计动作 |
|---|---|---|---|---|---|---|
| Submission | submitted | 撤回 | 学生/组长 | 未截止且未被查收 | withdrawn | withdraw_submission |
| Submission | submitted | 助教退回 | 助教 | 已查收且不合格 | returned | return_submission |
| Submission | returned | 重新提交 | 学生 | 迭代未截止 | submitted | resubmit |
| Submission | reviewing | 助教查收 | 助教 | 文件有效 | received | process_check |
| Project | draft | 发布 | 教师 | 权重和为100%、时间合法 | published | publish_project |
| PeerReview | draft | 提交 | 学生 | 未过互评截止 | submitted | submit_review |
| 成绩 | 未发布 | 发布成绩 | 教师 | 过程分/终评/调整完成 | published/只读 | publish_grades |
| 成绩 | published | 撤回发布 | 教师 | 无未处理申诉或确认作废快照 | 未发布 | unpublish_grades |

### 2.6 互评与成绩规则清单
1. 互评分配：仅 `published` 且 `review_open=true` 的项目分配；候选目标为非本人团队且已提交有效成果的团队；每人最多 3 个，候选不足按实际分配；写入 `review_assignments`，同一 reviewer+target 唯一。
2. 极值剔除：n≥5 去一个最高一个最低取平均；3≤n<5 不去极值直接平均；n<3 标记“互评样本不足”，需教师确认。
3. 缺评扣分：互评截止时 `status≠submitted` 记为缺评；每缺 1 个扣 X 分，最多扣 Y 分；扣分进入成绩计算明细。
4. 成绩发布：发布时生成 `grade_snapshots` 和 `grade_items`，成绩只读；撤回发布前存在未处理申诉则拒绝撤回。
5. 成绩申诉：申诉期内学生只能对本人成绩提交一次；教师可维持或调整；调整必须撤回发布、原快照作废、重新计算生成新快照。
6. 团队人数：3–5 人；组队截止后学生不能自行变更；教师例外调整必须填写理由并写审计。

## 四、体系结构设计
### 4.1 分层架构
采用经典三层B/S分层架构：


1. **表现层（前端SPA）**
- 文件：`index.html` + `app.js`
- 职责：页面渲染、DOM操作、表单校验、弹窗交互；维护前端全局状态；调用后端REST API；处理用户点击跳转；本地存储侧边栏状态、激活项目id。
- 输出：HTML DOM页面，向服务端发送HTTP请求。

2. **业务逻辑层（Flask后端）**
- 职责：会话登录鉴权，CSRF校验；角色权限判断；业务规则校验（权重和为100%、截止时间拦截、团队人数限制）；业务流程调度；文件接收校验；成绩计算；生成通知；写入审计日志；组装返回前端的bootstrap大数据包。
- 接收：前端HTTP JSON / FormData请求。
- 向下调用数据库读写，向上返回JSON响应、文件下载流。

3. **数据持久层（SQLite + 文件存储）**
- SQLite数据库：存储全部业务表，用户、课程、项目、团队、提交记录、互评、成绩、通知、审计日志。
- 文件系统：`uploads`目录存储上传PDF/ZIP/MP4成果文件。

### 4.2 系统部署架构
- 运行模式：桌面演示模式可以使用waitress作为WSGI服务，浏览器本地访问；也可部署在服务器。
- 客户端：任意现代浏览器，不需要安装客户端软件。
- 服务端：Python运行环境；SQLite数据库文件、上传文件目录；环境变量可配置数据目录、密码、密钥。

### 4.3 数据流：系统启动主流程
1. 浏览器访问`/`加载index.html，加载app.js，调用`start()`。
2. 前端调用`GET /api/session`检查登录状态。
3. 未登录：渲染登录界面；登录成功保存csrfToken，调用`/api/bootstrap`获取全部业务数据。
4. 后端`bootstrap`接口：同步截止通知，查询课程、项目、团队、提交记录、通知、日志，组装完整数据包返回前端。
5. 前端存入`state.data`，调用`renderShell()`渲染侧边栏导航，调用`render()`渲染当前业务页面。
6. 用户点击页面按钮触发action，调用`bindActions()`绑定事件，调用`api()`向后端提交请求，请求完成调用`load()`刷新页面数据。

### 4.4 核心业务数据流示例（提交迭代成果）
1. 学生前端点击上传按钮打开模态框，选择本地文件。
2. 前端校验文件后缀，FormData携带文件，POST请求`/api/submissions/{iteration_id}`。
3. 后端鉴权：判断用户角色，校验是否为本团队负责人或被分配任务成员；校验迭代是否过期；校验团队人数是否3‑5人。
4. 后端校验文件扩展名、文件头真实格式；生成uuid文件名写入uploads目录。
5. 数据库写入submissions记录与submission_versions版本记录；更新team状态；写入audit审计日志。
6. 返回成功JSON，前端调用`load()`重新拉取bootstrap数据刷新页面，弹出toast提示。

### 4.5 安全架构要点
1. 会话登录session保存user_id，后端校验用户角色。
2. POST/PUT/PATCH/DELETE请求强制校验X‑CSRF‑Token。
3. 密码存储bcrypt加盐哈希，不保存明文；5次密码错误锁定账号15分钟。
4. 前端全部输出使用`esc()`做HTML转义，防御XSS。
5. 数据库使用参数化查询，防御SQL注入。
6. 审计日志SHA‑256哈希链，防止篡改，管理员接口可校验完整性。
7. 文件上传校验后缀+文件魔数双重校验，拒绝非法文件。
8. 乐观锁lock_version，防止多人并发提交覆盖数据。

### 4.6 权限矩阵表

| 功能/数据 | 教师 | 助教 | 学生 | 管理员 |

### 4.8 审计链与密码安全补充说明
1. 密码统一为：“密码采用 bcrypt 加盐哈希存储；连续 5 次登录失败锁定账号 15 分钟，失败次数与锁定截止时间记录在 users 表。”
2. 审计链：“首条日志 previous_hash 为固定创世哈希；entry_hash=SHA-256(previous_hash+规范化业务字段)；写入审计日志在事务内串行执行，避免并发分叉；`verify_audit_chain()` 按 id 升序全量校验，发现 previous_hash 不匹配或 entry_hash 重算不一致即报告断链位置；匿名互评相关审计 detail 对非管理员脱敏。”

### 5.8 接口错误处理与权限约定

接口全部为 REST 风格，`GET` 查询，`POST` 执行业务操作；写操作需在 header 携带 `X-CSRF-Token`；返回统一 JSON 格式 `{"ok":bool, "message":"xxx", ...data}`。5.1–5.6 的接口表统一增加“权限角色、请求关键字段、成功返回、主要错误”四列。

**错误码约定：**

| 错误码 | 含义 | 前端处理 |
|---|---|---|
| 400 | 业务校验失败 | toast 展示业务提示，不跳转 |
| 401 | 未登录/会话失效 | 跳转登录页 |
| 403 | 权限不足/CSRF 校验失败 | toast 提示无权操作 |
| 404 | 资源不存在 | toast 提示资源不存在 |
| 409 | 乐观锁冲突/状态冲突 | 提示刷新后重试 |
| 422 | 字段校验失败 | 表单字段提示 |
| 500 | 系统异常 | 统一异常提示，记录日志 |

**权限与安全约定：**

1. 每个接口必须在设计表中标明允许访问的角色；后端按角色和业务状态双重校验。
2. 学生只能访问本团队数据及分配给本人的匿名互评任务；教师/助教按课程和项目范围访问；管理员按管理职责访问。
3. `/api/bootstrap` 按当前角色和选中项目裁剪返回数据，不返回无权查看的互评人身份、其他团队文件路径和审计明细。
4. 匿名互评场景下，教师/助教端默认脱敏互评人身份，管理员仅在审计需要时可追溯。
5. 无有效 `X-CSRF-Token` 的写操作返回 403；未登录访问受保护接口返回 401；越权访问返回 403。
6. 业务异常返回 400/409/422 时前端保留当前页面并提示；401 跳转登录；403 仅提示无权操作。


## 六、总结
### 6.1 设计完成情况
本平台完成课程项目协作评审系统完整设计，基于需求分析报告，划分模块、完成领域类设计、三层B/S体系结构、REST接口设计。
系统实现全部核心业务：课程项目发布、学生团队管理、迭代成果提交版本管理、匿名同伴互评、助教过程检查、多维度成绩加权自动核算、个人成绩防搭便车折算、成绩快照归档导出、站内通知、哈希链审计日志，完整覆盖教师、助教、学生、教务管理员四类角色业务场景。
系统在安全层面做了完整防护：CSRF防护、密码加盐、文件校验、SQL参数化查询、XSS转义、乐观锁并发控制、审计日志篡改检测。

### 6.2 系统优点
1. 业务闭环完整，贴合高校软件工程课程项目制教学真实场景，完整覆盖从任务发布到成绩归档全流程。
2. 权限粒度精细，角色+业务状态双重校验；数据做行级隔离，互评双盲机制保护学生隐私。
3. 可追溯性强，所有关键操作写入带SHA‑256哈希审计链，支持篡改校验，满足教学审计需求。
4. 成绩计算规则完备，支持互评极值剔除、个人折算系数、缺评扣分，解决搭便车、人情分教学痛点。
5. 前后端分离，接口清晰，前端为原生JS SPA，后端接口易于扩展维护。

### 6.3 存在不足与改进方向
1. 当前使用SQLite，适合课程演示；如果面向大规模多班级生产部署，需要迁移MySQL/PostgreSQL，优化数据库索引。
2. 文件存储本地磁盘，生产环境建议接入对象存储OSS，做文件备份。
3. 没有接入学校统一身份认证，当前为演示账号登录，后续可以扩展SSO单点登录。
4. 已建立后端接口与前端页面自动化测试，后续可继续补充桌面端打包验证和复杂交互流程测试。
5. 通知仅实现站内信，可以扩展邮件推送、消息网关对接。

### 6.4 课程设计体会
通过本系统设计，完整实践软件工程流程：从需求分析，再到系统设计（类、架构、接口），理解B/S分层架构，掌握REST接口设计，认识业务状态驱动、权限控制、审计追溯在教学类业务系统中的重要性；同时体会业务规则对代码实现的约束，很多bug来源于业务边界场景没有处理。设计时需要兼顾功能、安全性、可用性，不能只实现核心流程，更要处理异常、并发、权限、数据隐私等边缘场景。
